# 程序 Agent 能力测试任务单

## 使用方式

一次运行只发一张任务单。除“阶段 1”外，后续任务需在前置阶段通过并由测试者确认后再派发。禁止 agent 自行选择并实现所有后续功能。

## 阶段 1 可复制提示词

> 请在【目标游戏项目目录】实现策划包的阶段 1 MVP。先阅读 00-策划包说明.md 和 01-最小MVP.md；只从 02-共用核心规则.md 读取七种方块出生占格表。不要实现 02 中正式 SRS、锁定延迟或其他后续规则，也不要实现策划包标记为“不做”的内容。先检查目标项目的现有结构和运行方式，沿用现有技术栈。完成后启动游戏，用可复现步骤检查碰撞、旋转、软降、硬降、消行、暂停、结束和重开。交付改动摘要、启动命令、实际执行的检查、验收结果和未覆盖项；不要把未实际运行的检查写成通过。若你发现策划与现有项目约束冲突，先列明冲突及影响，再做最小范围的处理。

## 阶段 1：MVP 实现

目标文件：测试者提供的空白游戏项目。需求依据：01-最小MVP.md 与 02-共用核心规则.md 中的方块出生形状表。

交付要求：可启动游戏、可玩一局；实现任务书所列键位；提供满行、碰撞、游戏结束和重开的可复现验证步骤；报告实际改动文件与执行过的检查。禁止实现 MVP 明确排除的高级系统。

## 阶段 2：规则升级

将 MVP 的简化旋转升级为 02-共用核心规则.md 的 SRS、隐藏行、锁定延迟、Move Reset 和 7-bag 规则。提交表驱动逻辑用例，覆盖 SRS 每种转向和踢墙候选，不得只证明普通旋转成功。

## 阶段 3：默认模式

按 03-默认模式-马拉松.md 增加等级、速度、计分、Combo、B2B、结算和本地最佳分。每张子任务单只实现一组相关规则，例如先做进度/速度，再做得分/连击，最后做 UI/存档。

## 阶段 4：单独模式

每次只实现一个模式：04 Sprint、05 Ultra、06 Daily。实现前先对照共用规则，禁止复制一套独立玩法引擎。

## 阶段 5：反馈打磨

从 07-视觉交互与音频方向.md 中选一个反馈目标，例如方块可读性、消行反馈或结算再开体验。每次限一个目标并提供前后截图或可重复步骤。

## 每张任务单的验收字段

- 目标：本次要改变的玩家可见行为。
- 范围：允许修改的功能和文件。
- 不做：明确排除的相邻功能。
- 验收：可复现的操作和预期结果。
- 回归：改动影响到的既有行为及对应检查。
- 证据：启动命令、检查结果、截图或日志路径。
- 未完成：实际未覆盖的项目必须明示；不能把“代码已写”报告成“功能已验证”。

## 测试者观察记录

每次试验建议记录：任务原文、首次交付是否可玩、需求遗漏数、规则错误数、返工轮次、可复现验收通过项、总耗时和模型用量。记录用于比较 agent 的程序能力，不把审查模型的一句 PASS 当作事实证据。
